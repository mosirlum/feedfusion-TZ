## What this business is

Feed Fusion Tanzania sells animal feed (fish feed, poultry feed) through a physical shop. Suppliers deliver stock → stock goes into inventory → walk-in customers are served by sales staff → payment is cash, bank transfer, or mobile money, and can be the full amount or a partial deposit with the balance collected later (credit sales, added 2026-09-12 — see judgment call #50; originally "cash, immediate, in full" only) → goods leave with the customer → owner needs to see sales, stock, cash, and profit at any time.

Full requirements live in `docs/mvp-spec.md` and `docs/mvp-addendum.md`. **Read those before implementing any sales, stock, or pricing logic** — the business rules (BR-01 through BR-34) are not optional and several of them exist specifically to prevent real financial loss (overselling, silent stock edits, undocumented discounts).

**`docs/decisions-log.md` is the running record of every decision made outside the main spec** — check it before assuming something is still open. Currency (TZS only), the discount limit being global rather than per-user, manual discount entry, and the A4 receipt format are all settled there.

## Non-negotiable rules (the ones most likely to get broken by a careless implementation)

1. **Stock is never edited directly.** Every change to a product's quantity happens through a `stock_movements` row (purchase, sale, void reversal, adjustment, count correction). Current stock = sum of movements. Never add a "current_stock" column you write to directly.
2. **Sale completion is one atomic transaction.** Validate stock → create sale → create sale items → deduct stock → record movements → calculate profit → generate invoice number → audit log. All or nothing. If any step fails, the whole sale rolls back.
3. **Concurrent sales must never oversell.** Stock validation happens again at the moment of commit (row-level lock or equivalent), not just when items are added to the cart.
4. **Selling price only changes via an approved price proposal.** See `price_proposals` table. Owner edits are auto-approved; sales-user proposals sit as `PENDING` until the owner approves them. A product with no approved price cannot be sold.
5. **Discounts are a line-item adjustment, never a price edit.** `sale_items.unit_price` stays the product's real price; `discount_amount` is a separate, visible field. Reports and cash-expected use the post-discount total.
6. **Completed sales are never deleted.** Only voided (status change + reversing stock movement), and only by an authorized user.
7. **Every important action needs a `created_by` / audit log entry**, especially: sale completion, void, price approval, discount above a user's limit, stock adjustment, stock count.

## Tech stack

- Backend: Node.js, TypeScript, Express, PostgreSQL (raw SQL or a lightweight query builder — avoid a heavy ORM's abstraction hiding the transaction boundaries above)
- Frontend: React + Vite + TypeScript
- Auth: JWT session, role-based (`owner`, `sales`, optionally `manager` later)
- DB migrations: plain SQL files in `db/migrations/`, applied in order — no framework-specific migration DSL unless you have a strong reason

### Frontend design system

**Redesigned app-wide 2026-09-12 (see judgment call #56) — superseding the original logo-sampled palette described below only where it conflicts.** Brand colors were originally sampled directly from the supplied logo and `docs/receipt-template.html` — green `#3B6D11` and blue `#185FA5`. The sidebar/login panel used a `green → blue` gradient echoing the logo's infinity-loop mark; the app now uses a deeper forest-green identity (`green.600 #1c7d4f`, `green.700 #124a35`) approved by the owner from a dashboard mockup, with the sidebar staying a fixed dark gradient regardless of theme. Typography is Manrope (headings, `font-display`) + Inter (body, `font-sans`), both loaded in `index.html`. The app now supports a real light/dark theme toggle (`Tailwind darkMode: 'class'`, `frontend/src/context/ThemeContext.tsx`, toggle button in `AppShell.tsx`'s topbar) — persisted to `localStorage['feedfusion-theme']`, **defaulting unconditionally to light** (fixed 2026-09-12, judgment call #58 — it originally fell back to the OS/device dark-mode preference, which meant visitors with a dark-mode device landed on dark without ever choosing it), with a blocking inline script in `index.html`'s `<head>` to prevent a flash of the wrong theme on load — that script must stay in sync with `ThemeContext.tsx`'s own default logic. All screens are built from the shared primitives in `components/ui/index.tsx` — extend that file rather than one-off styling a new page; this is also why the redesign could reach nearly every screen by editing under 20 shared files instead of all ~24 pages individually.

**Printable documents are deliberately excluded from dark mode.** `components/ReceiptView.tsx`, `pages/QuotationViewPage.tsx`, and `pages/ReportsPage.tsx` (which embeds a `.print-area` inside its tab content, CLAUDE.md #42) must never receive `dark:` text/background utility classes — Tailwind's `dark:` variant is driven purely by the `.dark` class on `<html>` and is **not** suppressed by `@media print`, so printing a receipt/quotation/report while the app is in dark mode could silently produce invisible (e.g. white-on-white) output otherwise. These three files render light-only regardless of the app's theme, by design, not by oversight — don't "fix" this without re-solving the print-safety problem first.

## Working conventions for Claude Code sessions

- **Before writing sale/stock/pricing/discount logic**, re-read `docs/mvp-spec.md` sections 12, 15, 16 and `docs/mvp-addendum.md` in full. Don't reconstruct the rules from memory of this conversation — the docs are the source of truth.
- **One feature per session where possible.** This project splits cleanly into parallel-safe chunks: `auth`, `products+categories`, `purchases+suppliers`, `sales/POS`, `cash+reports`, `stock-count+adjustments`. Sales/POS touches the most shared logic (stock, pricing, discounts) — don't run it in parallel with another session also touching `stock_movements` or `sale_items` without merging carefully.
- **Money is stored as integers (cents/lowest unit) or `NUMERIC`, never `FLOAT`.** TZS has no subunit in practice, but still avoid float for currency — use `NUMERIC(14,2)` or integer shillings.
- **Every migration is additive and forward-only** during MVP build — no destructive schema changes without flagging it explicitly in the session summary.
- **Write the failing scenario as a test before the happy path** for anything touching Section 16/17 (concurrent sales, insufficient stock) — these are the rules most likely to silently break.

## Updating an already-running install

Whenever a new file appears under `backend/db/migrations/`, an already-running install needs two commands, not a fresh `npm install` — `npm run migrate` only applies migrations it hasn't seen yet (each runs once), so it's safe to re-run:

```
cd backend
npm run migrate    # applies any new migrations (currently up to 019_invoice_terms.sql)
npm run seed        # idempotent — only adds rows that don't already exist by name
```

`npm run dev` (tsx watch) picks up backend code changes automatically; the frontend's `npm run dev` (Vite) does the same. Neither needs a restart for a migration — just re-run the two commands above, then refresh the browser.

## Flagged judgment calls & deviations from the docs

The full rebuild required a few real decisions the docs don't spell out, or one place where two docs disagree. Each is called out here rather than resolved silently, per this project's standing instruction:

1. **`sales.customer_name` column added, not in `docs/database-schema.sql`.** `decisions-log.md` item #8 says a sale's customer name is optional and implies it's captured, but the original schema has no column for it at all. Added `sales.customer_name VARCHAR(160)` in migration `004_sales.sql` to close that gap. If this is wrong, it's a one-line migration to drop. **This is exactly the practice that caused the real, install-breaking bug fixed in #48 below — editing `customer_name` directly into `004_sales.sql`'s `CREATE TABLE` instead of adding a proper follow-up `ALTER TABLE` migration meant it only ever took effect on a database where migration 004 hadn't already run.** Every schema change from here on is a new numbered migration file, never an edit to one already shipped.
2. **`POST /sales` body shape fixed to match `api-reference.md`'s documented example.** The docs' JSON example is snake_case (`product_id`, `payment_amount`, `discount_pin`); the handler originally read camelCase field names, which would have silently rejected every request built against the documented contract. Fixed in `sales.controller.ts` to read the documented snake_case and translate internally — flagging in case any external integration was already built against the camelCase version.
3. **Discount "PIN" (BR-32) is the owner's account password**, verified via `bcrypt.compare` against every active owner, because the schema has no dedicated PIN column. A short numeric PIN column would be a reasonable follow-up if typing a full password at the till is too slow in practice. **Superseded 2026-09-13 (CLAUDE.md #66) — the owner-PIN gate was removed entirely**, at the owner's own request, rather than ever getting that dedicated PIN column. Kept here for history.
4. **A FIXED-amount discount is converted to an effective percentage** (`discount_amount / line_subtotal`) to compare against `business_settings.default_max_discount_pct`, since the limit is stored as a percentage but staff can enter either type. Confirmed with the user before implementing.
5. **Multi-line purchase cost allocation** (`purchases.service.ts allocateCosts`): `mvp-spec.md` Section 10 only worked a single-item example. Additional costs are allocated proportionally by each line's pre-additional-cost subtotal share — a standard, defensible method, but not the only possible one.
6. **Only one PENDING price proposal per product at a time** (`price_proposals.service.ts`) — a second proposal while one is pending is rejected with `409 PENDING_PROPOSAL_ALREADY_EXISTS` rather than allowed to queue.
7. **"Can see unpriced products" is derived from the verified JWT role, not the `?role=owner` query parameter** that `api-reference.md`'s GET `/products` line literally describes — trusting a client-supplied role parameter for that decision would be a real authorization bypass. The frontend still sends the parameter (harmless) but the backend ignores it.
8. **`PATCH /users/:id`'s documented `max_discount_pct` field is not implemented.** `decisions-log.md` settled the discount limit as one global value in `business_settings`, not per-user — there's no per-user column for it. That part of `api-reference.md` is stale.
9. **Reports → Users activity** is scoped to `role = 'sales'` (the population Section 26 describes as needing a non-accusatory performance signal); owners don't appear in their own comparison table.
10. **Cash counts have no uniqueness constraint per day** — the schema doesn't enforce one, and nothing in the docs says a day can only be counted once, so recounting the same date is allowed (each is its own historical row, per Section 21's "stores a historical record").
11. **`expenses.expense_type` added** (migration `009_expense_type_and_product_status.sql`), not in the original schema or spec — confirmed with the owner on 2026-09-11. Classifies an expense as `PER_PURCHASE`, `MONTHLY`, or `PERIODIC` (default `PERIODIC`) purely for reporting, and is intentionally **not** linked to a specific `purchases` row. The reasoning, also called out in `expenses.service.ts`: freight/transport that's part of a supplier's invoice already lives in `purchases.additional_costs` and is allocated into unit cost there — that's what makes the Section 24 "purchase's 150,000 + 30,000 transport" example work today, with no separate expense entry needed. `PER_PURCHASE` in the Expenses module is reserved for a different case: an incidental cash cost tied to a delivery that is *not* on the supplier's invoice (e.g. loading labor paid directly to the truck crew). Recording the same transport cost in both places would double-count it into inventory value/COGS — the Expenses page's "Type" field carries an inline warning about this.
12. **`PATCH /products/:id` added** (migration 009 also — no schema change needed, `products.status` already existed), not in `api-reference.md`. Lets the owner deactivate/reactivate a product ("remove" from the sellable/POS list) — mirrors the existing active/inactive pattern for users and suppliers. Never deletes a product row, since purchase history and stock movements reference it.
13. **Inline "add new" for Suppliers (Purchases page) and Categories (Products page)**, requested by the owner so a first-time supplier or a new product category (e.g. "Poultry Feed" / "Fish Feed") doesn't require leaving the form. Both call the existing `POST /suppliers` / `POST /categories` endpoints — no new backend routes, just frontend UX.
14. **`db/seed.ts` catalog corrected to the owner's real product list** (2026-09-11): Poultry Feed → KPC-30, KPC-20, KBC-35, KLC, Creep Feed (sold by the bag); Fish Feed → Powder, Crumble, 1mm, 2mm, 3mm, 4mm (sold by the kg). The prior seed used "KPC-30/KPC-20" as *fish*-feed pellet grades — that was this project's own placeholder guess from before the real catalog was known, not a spec requirement. Anyone who already ran `npm run seed` against the old catalog will have 3 old demo products (KPC-30 Fish Feed, KPC-20 Fish Feed, Layer Mash) alongside the new 11 after re-seeding — deactivate them from the Products page (judgment call #12) rather than deleting, since they may already have purchase/stock history.
15. **`purchase_additional_cost_lines` table added** (migration `010_purchase_cost_lines_and_list.sql`), not in the original schema. The owner wants the Purchase form's "additional costs" broken into named lines (e.g. "Delivery / Transport", "Loading Labour", plus a free "+ Add other cost") instead of one lump number, so the breakdown survives and can be viewed later per purchase. `purchases.additional_costs` and `purchase_items.allocated_additional_cost` are unchanged and remain the only numbers actually used for inventory value/COGS math — when `additionalCostLines` is sent, its sum simply BECOMES `additional_costs`; the lines are a breakdown of that total, never added on top of it. `POST /purchases` still accepts a flat `additionalCosts` for backward compatibility if no lines are sent.
16. **`GET /purchases` (list) added** — also migration 010, not in the original doc. The Purchases page's "Recent Purchases" panel previously only showed what was created in the current browser session (client-side state, lost on refresh); it now reads real history from the database.

Expenses start empty and are only added via "+ Add expense", which opens a cost-type select (Labour charge / Transport-Delivery / Loading fee / Storage fee / Other, with a free-text label for "Other") plus an amount — replacing the earlier pre-filled expense boxes.

20. **Fixed a real "internal error" on Record Purchase** (2026-09-11): the frontend's auto-generated reference number (used when the owner leaves Reference # blank) was `PO-<date>-<last 4 digits of Date.now()>` — only 4 digits of entropy, cycling every 10 seconds, so a quick resubmit on the same date could generate the same reference twice. `purchases.reference_number` is `UNIQUE`, so the second insert threw a raw Postgres error that reached the owner as a bare "internal error" toast. Fixed two ways: the generator now uses the full timestamp plus a random suffix (`PO-<date>-<full timestamp>-<random>`, effectively collision-free), and `purchases.service.ts` `createPurchase` now catches a unique-violation on `reference_number` specifically and throws a proper `409 REFERENCE_NUMBER_ALREADY_EXISTS` with a clear message instead of letting a raw DB error bubble up as "internal error" — defense in depth in case of a genuine manual duplicate.
21. **Added `npm run db:reset` (`backend/db/reset.ts`)**, not in the original spec — the owner asked to wipe all seeded/demo data to learn the app from a genuinely empty system. `TRUNCATE ... The backend re-checks the same shape and returns `400 INVALID_PHONE_FORMAT` — defense in depth in case a request ever bypasses the frontend. The phone field stays optional everywhere; validation only runs when something was actually typed.

28. **"Could not record this purchase" investigated across several rounds (2026-09-11) — first two attempted fixes treated the symptom, the real bug was found on the third pass.** The owner reported an error toast on every single "Record purchase" click, immediately, with the purchase nonetheless showing up after a refresh. What actually happens: `createPurchase`'s final step reads the just-inserted row back from the database to send to the browser, but it was doing that read via `purchasesRepo.findPurchaseById(purchase.id)` — no client argument, so it used the shared `pool` rather than the transaction's own connection. The insert hadn't committed yet at that point (`COMMIT` runs after the callback returns), and under Postgres's normal READ COMMITTED isolation a *different* connection can never see another transaction's uncommitted rows — so that read deterministically came back empty, `createPurchase` returned `null`, and the frontend crashed immediately trying to read `res.data.reference_number` off of `null` — while the `INSERT` itself, unaffected by any of this, went on to commit normally a moment later. This explains every symptom at once: instant (no network wait involved), 100% reproducible (a logic bug, not a timing fluke), and the purchase genuinely there afterward. Fixed by giving `findPurchaseById` (and `getAdditionalCostLines`) an optional `queryable` parameter (defaulting to `pool` for normal reads like `GET /purchases/:id`) and having `createPurchase` pass its transaction's `client` through, so the read-back happens on the same connection that can see its own uncommitted work.
    - Two earlier attempts before this one narrowed things down but didn't fix the real bug, and are worth knowing about since their code is still in place as reasonable-but-unrelated hardening: `backend/src/server.ts` runs a `SELECT 1` every 4 minutes to stop Neon's serverless Postgres from auto-suspending during active use (a real thing, just not what was happening here), and `PurchasesPage.tsx`'s `handleSubmit` has a `findJustRecordedPurchase` recovery path that re-checks recent purchases when a request fails with no HTTP response at all (`axios.isAxiosError(err) && !err.response`) — also harmless to keep, since a request that's truly lost in transit (as opposed to this bug, which always returns a real 201 with a `null` body) is still a real possibility on any deployment.
